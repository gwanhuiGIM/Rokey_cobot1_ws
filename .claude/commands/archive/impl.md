# 구현 루프: $ARGUMENTS

## 규칙 (위반 시 즉시 중단)
1. 계획에 없는 파일은 수정하지 않는다. 필요하면 먼저 계획 변경을 나에게 제안한다.
2. **테스트 먼저**. 구현 전에 실패하는 테스트를 만들고, 그것이 실패하는 것을 확인한 뒤 구현한다.
3. 태스크 1개 완료 → `./scripts/verify.sh <pkg>` 실행 → 통과 확인 → 다음 태스크. 건너뛰지 않는다.
4. 확실하지 않은 API는 쓰지 말고 `# UNVERIFIED:` 주석 + 나에게 질문.
5. 실기(dsr01) 대상 모션 명령을 **실행**하지 않는다. 코드 작성까지만 하고 실행은 나에게 넘긴다.
6. 에러가 3번 연속 같은 지점에서 나면 임의 수정을 멈추고 `/debug`로 전환한다.

## ROS 2 체크리스트 (각 태스크 완료 시 자기 점검)
- [ ] QoS를 명시했는가? 퍼블리셔/서브스크라이버 QoS가 호환되는가?
- [ ] 서비스/액션 호출이 블로킹인가? 콜백 안에서 동기 호출하고 있지 않은가?
- [ ] 파라미터를 `declare_parameter()`로 선언했는가? 하드코딩 없는가?
- [ ] 노드 종료 시 `destroy_node()` / 리소스 해제 경로가 있는가?
- [ ] 네임스페이스와 리매핑이 런치 파일과 일치하는가?
- [ ] TF 프레임 이름과 좌표계 방향이 문서와 일치하는가? 단위는 SI(m, rad)인가?
- [ ] `setup.py` / `CMakeLists.txt` / `package.xml`에 새 파일·의존성을 등록했는가?

## 태스크 완료 직후 (필수)
verify.sh가 PASS한 뒤, @cross-review 서브에이전트를 호출해 방금 작성한
코드를 백지 상태에서 재검토받는다. 결과는 아래에 그대로 첨부한다.
cross-review가 Blocker를 지적하면 "완료"라고 쓰지 말고 먼저 대응한다.
"의도를 알 수 없는 곳"에 항목이 있으면 이름이나 주석을 고친 뒤 넘어간다.

## 매 태스크 종료 시 출력 형식
```
### 태스크 N: <제목>
- 변경 파일: <경로 목록>
- 왜 이렇게 했는가: <2줄>
- verify.sh 결과: PASS / FAIL (FAIL이면 로그 마지막 20줄)
- 미검증 항목: <UNVERIFIED 목록 또는 "없음">
- 다음 태스크: N+1
```

verify.sh가 FAIL이면 **"완료"라고 쓰지 마라.** 원인을 보고하고 멈춘다.
