# 코드 리뷰

## 변경 내용
- 변경 파일: !`git diff --name-only HEAD`
- Diff: !`git diff HEAD`
- 추가 대상: $ARGUMENTS

## Stage 1 — 기능 적합성 (여기서 막히면 Stage 2로 가지 않는다)
1. 이 변경이 계획 문서(`docs/plans/`)의 요구사항을 **실제로** 충족하는가? 빠진 항목을 나열하라.
2. 성공 판정 기준을 이 코드로 측정할 수 있는가?
3. 계획에 없던 변경이 섞여 있는가? 있으면 지적하라.

## Stage 2 — 품질 (ROS 2 관점)
심각도별로 보고한다. **Blocker가 하나라도 있으면 머지 불가로 판정하라.**

| 심각도 | 파일:라인 | 문제 | 구체적 수정안 |
|---|---|---|---|

점검 항목:
- **동시성**: 콜백 내 동기 서비스 호출(데드락), 콜백 그룹 설정, 공유 상태의 락
- **QoS/수명주기**: QoS 불일치, 노드 종료 시 정리, 재연결 처리
- **자원**: 이미지/포인트클라우드 복사 남발, 메모리 누수, 파일 핸들
- **에러 처리**: 예외 삼키기(`except: pass`), 하드웨어 실패 시 안전 상태 진입 여부
- **재현성**: 시드 고정, 하드코딩된 절대 경로, 머신 종속 설정
- **의존성**: numpy/pydantic/opencv 제약 위반 여부
- **보안**: 자격증명 하드코딩

## 금지
- 스타일 지적(포매팅)은 보고하지 마라. 린터의 일이다.
- 요청 범위 밖의 리팩터링을 제안하지 마라.
- 문제가 없으면 억지로 만들어내지 말고 "Blocker 없음"이라고 쓰라.
